# Draw Page And Structured Reading Design

Date: 2026-04-23
Scope: Standalone draw page, structured AI reading pipeline, admin prompt/config expansion
Status: Approved in conversation, pending written spec review

## Summary

Replace the current homepage draw section with a standalone draw experience page built around a ritual-style interaction flow. The new flow starts on a dedicated draw page, opens a question-entry modal, triggers both draw generation and AI interpretation as soon as the question is confirmed, then plays a staged card ritual where three cards are revealed one by one while the remaining cards scatter away.

The client ultimately presents:

- one short overall judgment
- three per-card interpretations with upright/reversed orientation
- a longer question-specific analysis
- a locked “insight” action

The “insight” content is already generated by the AI response, but remains hidden behind a fake 1-yuan unlock modal. That modal also displays a roast line returned by the API, with different copy depending on whether the user hypothetically pays or refuses.

This is both a UX redesign and a data-contract expansion.

## Goals

- Move draw/reading into its own premium-feeling page
- Make the draw sequence feel ceremonial, not like a form submission
- Start AI work as early as possible so interpretation can arrive during the animation
- Expand AI output from a simple summary into a structured, parseable response
- Keep prompt authoring editable from the admin
- Preserve fallback behavior when the configured model fails or returns malformed JSON

## Non-Goals

- No real payment integration in this phase
- No user accounts or purchase persistence
- No backend queueing system or websocket infrastructure
- No overhaul of the archive, homepage hero, or admin card editor beyond what this feature needs

## Chosen Product Direction

The approved direction is:

- homepage relationship: `replace homepage draw section with entry to standalone page`
- entry style: `simple scene first, question modal after explicit start`
- draw animation style: `ritual`
- overall experience: `full ritual version`

## User Experience Flow

### 1. Homepage Entry

The homepage no longer contains the full draw interaction. Instead it contains a concise CTA that routes the user to the dedicated draw page.

Recommended CTA label:

- `开始抽三张`

Homepage responsibility becomes navigation, not execution.

### 2. Draw Page Idle State

The draw page opens as a dedicated dark ritual scene. It should not feel crowded with UI. The scene includes:

- a concise title / framing line
- a short explanation of what the user is about to do
- a single primary CTA

The page is quiet until the user chooses to begin.

### 3. Question Modal

Clicking the primary CTA opens a mysterious but usable modal where the user enters the question they want insight on.

Requirements:

- one multiline input
- one primary confirm action
- one dismiss / close action
- clear placeholder guidance
- no extra settings exposed in phase one

### 4. Request Start

When the user confirms the question:

1. close or transition out of the question modal
2. immediately request `/api/readings/draw`
3. immediately request the new structured interpretation API using the returned draw payload
4. transition the page into ritual animation state

The AI request starts at question-confirm time, not after animation.

### 5. Ritual Animation

The animation sequence has explicit stages:

1. ritual stage activates
2. central deck or stacked card cluster appears
3. three cards are drawn one by one
4. each drawn card reveals its orientation
5. remaining cards scatter / dissolve away
6. the final three-card spread locks into readable positions

The pacing should be dramatic but disciplined. The page should clearly communicate “three cards were chosen,” not just “cards moved.”

### 6. Reading Result

After the cards settle, the results area presents:

- `summary`: one short judgment line, max ~80 Chinese characters
- `cardReadings`: three structured card readings, each tied to a card and orientation
- `analysis`: one longer explanation, max ~160 Chinese characters
- `insight` remains hidden
- `unlock insight` button opens fake paywall modal

If AI is still pending when cards settle, the cards remain visible while the interpretation area shows a ritual loading state.

### 7. Insight Paywall Modal

The insight button opens a fake payment modal.

The modal shows:

- a prompt asking whether to unlock the insight for 1 yuan
- one roast line for “paid”
- one roast line for “unpaid”

Phase one behavior:

- no real payment
- clicking either path only demonstrates the concept
- hidden `insight` content is not actually revealed yet unless we explicitly choose to simulate it later

## Design Decisions

- Color palette: deep obsidian, warm gold ritual lines, restrained cyan highlights
- Typography: serif for stage titles and result highlights, sans-serif for interaction and explanatory text
- Spacing system: large empty ritual stage first, denser information layout only after reveal
- Border-radius strategy: large scene and modal radii, tighter result cards, consistent with current site system
- Shadow hierarchy: revealed cards are strongest, ritual overlays second, reading panels lightest
- Motion style: staged, sequential, legible; no ambient movement that competes with the draw sequence

## Client State Model

The new draw page should be driven by an explicit UI state machine.

Recommended top-level states:

- `idle`
- `asking`
- `submitting`
- `drawing`
- `revealing`
- `waiting_for_reading`
- `resolved`
- `paywall`
- `error`

Supporting state should include:

- current question
- reading id
- draw payload
- structured interpretation payload
- animation phase / reveal index
- whether the insight modal is open
- whether the AI result came from configured provider or fallback

## Structured AI Contract

The current reading format is too small for the new experience. Replace it with a richer structure.

### Required Response Shape

```json
{
  "summary": "80字以内一句话评语",
  "cardReadings": [
    {
      "position": "现状",
      "cardName": "服务器宕机",
      "orientation": "正位",
      "reading": "80字以内标准解读"
    },
    {
      "position": "阻力",
      "cardName": "提示词工程师",
      "orientation": "逆位",
      "reading": "80字以内标准解读"
    },
    {
      "position": "建议",
      "cardName": "飞行模式",
      "orientation": "正位",
      "reading": "80字以内标准解读"
    }
  ],
  "analysis": "160字以内问题详解",
  "insight": "一条根据问题和抽卡得出的幽默行动建议",
  "paywallRoasts": {
    "paid": "付费版吐槽",
    "unpaid": "不付费版吐槽"
  }
}
```

### Requirements

- response must remain JSON only
- field names must be stable
- `cardReadings` length must be exactly 3
- `orientation` should align with the draw result
- roast strings are required because the paywall depends on them

## Admin Changes

The admin already supports:

- `baseUrl`
- `apiKey`
- `modelId`
- `systemPrompt`
- `userPromptTemplate`

That system should be retained and expanded only as needed for the new output format.

### Admin Requirements

- keep editing of `systemPrompt`
- keep editing of `userPromptTemplate`
- update defaults so they demand the new JSON schema
- clearly document supported template variables
- make it obvious that malformed output falls back to local interpretation

No new separate prompt fields are required yet unless the implementation becomes cleaner with separate unlock-roast instructions. Default recommendation is to keep one system prompt + one user prompt template.

## API Changes

### Existing Endpoints

- `POST /api/readings/draw`
- `POST /api/readings/interpret`

### Recommended Direction

Keep the draw endpoint, but upgrade the interpretation endpoint so it returns the structured response.

#### `POST /api/readings/draw`

Responsibilities:

- accept question
- generate three unique cards with orientations
- create reading record
- return `readingId`, `question`, `draws`

#### `POST /api/readings/interpret`

Responsibilities:

- accept `question`, `draws`, `readingId`
- call configured AI if available
- parse structured JSON
- validate shape
- fallback to deterministic local structure when parsing fails
- persist structured interpretation on the reading record
- return structured interpretation + provider info

No additional endpoint is strictly required in phase one because the insight is generated alongside the main interpretation and only hidden on the client.

## Data Model Changes

### Client Types

Replace the old simple `ReadingInterpretation` with a structured type.

Recommended shape:

- `summary: string`
- `cardReadings: Array<{ position; cardName; orientation; reading }>`
- `analysis: string`
- `insight: string`
- `paywallRoasts: { paid: string; unpaid: string }`

### Database

The existing `Reading.interpretation Json?` field can continue storing the richer structure.

Potential optional additions:

- `status` field for reading progress
- `provider` field

These are helpful but not mandatory for phase one if client state is sufficient.

## Fallback Strategy

Fallback must remain strong because the draw page experience depends on always completing.

Fallback behavior:

- if AI config is disabled, use local fallback
- if network call fails, use local fallback
- if AI output is non-JSON or wrong shape, use local fallback
- fallback should populate all required structured fields, including `insight` and both roast strings

The user should never end the ritual with empty results.

## Animation Architecture

The draw page needs deterministic, step-based timing.

Recommended implementation strategy:

- use React state + CSS transitions / keyframes
- avoid overcomplicated animation libraries unless sequencing becomes unmanageable
- drive reveal order from explicit timers or a reducer/state machine
- keep animation logic localized to the draw page, not spread across unrelated components

### Core Visual Beats

1. quiet stage
2. prompt confirmed
3. ritual overlay wakes up
4. deck materializes
5. first draw
6. second draw
7. third draw
8. remaining deck disperses
9. spread locks
10. interpretation reveals

## Page Composition Strategy

The draw page should likely be implemented as a dedicated top-level component rather than extending the current homepage component further. The homepage component is already carrying multiple responsibilities.

Recommended implementation split:

- route page wrapper for `/reading`
- focused draw scene component
- question modal component
- ritual animation component
- results component
- insight paywall modal component
- shared reading helper / parser logic in `lib`

## Migration Strategy

1. build the new `/reading` page
2. update homepage CTA to route there
3. remove the old homepage draw form and inline result block
4. retain the existing library and detail modal behavior untouched

This avoids partial dual-maintenance of two draw experiences.

## Risks And Mitigations

- Risk: animation and AI timing become coupled in a brittle way
  - Mitigation: drive them independently and synchronize only at reveal/result checkpoints
- Risk: model output deviates from schema
  - Mitigation: validate strictly and fallback immediately
- Risk: the page becomes too theatrical and slows repeat usage
  - Mitigation: keep the ritual sequence finite and tightly timed
- Risk: homepage loses utility after removing inline draw
  - Mitigation: make the CTA prominent and obvious

## Deliverable

A dedicated ritual draw page with staged three-card animation, early-start AI interpretation, a structured result contract, configurable admin prompts, and a fake 1-yuan insight unlock flow that already runs on fully generated hidden content.
